# Ferienkasse 1.3 – Architektur und Migrationsplan

Status: Vorbereitung, NICHT produktiv. main (1.2.1) bleibt unverändert.

## Ziele
- Eine PWA für iOS, Android und Desktop über bestehende GitHub-Pages-URL.
- E-Mail-OTP via Supabase Auth (persönliche Konten).
- Gemeinsame Reisen: alle eingeladenen Mitglieder dürfen Ausgaben erfassen, ändern und löschen.
- Reisemitgliedschaft wird serverseitig geprüft (Postgres RLS); Einladung nur durch Mitglieder, initial den Ersteller.
- Realtime-Benachrichtigung mit anschliessendem autorisierten Reload; keine geheimen Tokens im Repository.
- Offline-Daten über IndexedDB mit Mutations-Queue und Konflikterkennung anhand version-Spalte; nicht stillschweigend Last-Write-Wins.
- Private Belege im Storage, nur für Mitglieder der Reise zugänglich.

## Datenmodell
- trips(id UUID, name, date, currency, budget_cents, rates JSONB, categories JSONB, owner_id, version, created_at, updated_at)
- trip_members(trip_id, user_id, joined_at, PK(trip_id,user_id))
- trip_invites(id, trip_id, email, token_hash, expires_at, accepted_at, created_by)
- trip_people(id, trip_id, name, sort_order) – Abrechnungs-Personen unabhängig von Benutzerkonten.
- expenses(id, trip_id, date, name, category, payer_id, currency, amount_cents, rate, shares JSONB, custom JSONB, receipt_path, version, deleted_at, updated_by, updated_at)
- payments(id, trip_id, from_person_id, to_person_id, amount_cents, date, version, deleted_at)
- audit_events(id, trip_id, actor_id, entity_type, entity_id, action, created_at, old_data, new_data)

## Sicherheit
- Auth-User-ID ausschliesslich aus auth.uid(); nie aus untrusted Client-Feldern.
- RLS auf allen Tabellen und privaten Storage-Objekten. Keine service_role keys im Browser.
- SELECT/INSERT/UPDATE/DELETE für Mitgliedschaft prüfen; zusätzliche WITH CHECK-Prüfungen für trip_id.
- Einladungscode zufällig, kurzlebig, einmalig, gehasht in DB, Annahme ausschliesslich für eingeladene E-Mail.
- Schutz vor Selbsteskalation bei Mitgliedschaften: Einladungsannahme nur über geprüfte Serverfunktion.
- Quoten/Rate-Limits, Eingabevalidierung, Beleggrössenlimit, Lösch- und Backup-Konzept.
- GitHub Pages ist öffentlich: nur Supabase project URL und anon/publishable key im Frontend.
- Vor Livegang Security Review der RLS-Policies mit zwei unabhängigen Testkonten.

## Migration von 1.2.1
Aktuelles lokales Format: JSON version=1, localStorage-Schlüssel ferienkasse.pwa.v1.
1. Vor der Migration JSON-Backup herunterladen und auf zweitem Speicherort ablegen.
2. Importdatei lokal parsen und wie bisher validieren; nichts löschen.
3. Import-Vorschau: Reisen, Personen, Ausgaben, Zahlungen, Kategorien, Budget, Kurse, Belege, Salden.
4. IDs beibehalten, falls valide UUIDs; sonst deterministische Mapping-Tabelle für Referenzen.
5. Import in Staging-Transaktion mit import_batch_id und Idempotenzschutz; Belege separat in privatem Storage.
6. Vergleich der Summen, Personensalden, Anzahl Einträge und Beleg-Hashes; Fehler => keine Freigabe.
7. Benutzer bestätigt Aktivierung der Cloud-Reise; lokale Daten/Backup bleiben unverändert.
8. Import wiederholbar ohne Duplikate; kein automatisches Überschreiben bestehender Cloud-Reisen.
9. Rollback: Cloud-Reise deaktivieren und lokalen Stand aus Backup wiederherstellen.

## Rollout
1. Schema und RLS in isoliertem Supabase-Testprojekt.
2. Auth UI und Mitgliedereinladung.
3. Online CRUD, Belege, Realtime.
4. Offline Queue und Konflikt-UI.
5. Migration mit anonymisierten Beispieldaten.
6. Tests auf Safari iOS, Chrome Android, Desktop; danach optionaler Pilot.
7. Merge nach main erst nach Freigabe und Backup.

## Noch benötigt
Ein vom Benutzer angelegtes Supabase-Projekt und dessen project URL + publishable/anon key (KEIN service_role key), sowie konfigurierte E-Mail-OTP- und Redirect-Einstellungen. Bis dahin keine echte Anmeldung/Synchronisation.
